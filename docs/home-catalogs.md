# Home catalogs and plugin capability contract

Home lists enabled, non-builtin sources that explicitly advertise `catalogs` as one line of names under the search prompts, centred while it fits and otherwise scrolling sideways with faded edges like the prompts, at every width, ending with a neutral gear that opens Configuration’s Music sources tab when the server supports Configuration. Saved previews follow with no group heading; after the last, a right-aligned **Want Home to look different?** line ends with a neutral **Customise Home** button, shown only when pins exist. With no pins but some collections, Home shows no pinned section and no customisation banner. Customise Home with no pins offers source tiles and instructions to browse to a catalog and pin it; choosing a source closes the panel and opens that source. Each source tile shows the plugin icon, plugin name and navigation chevron, without a description or subtitle. Users open a source, navigate to any catalog or subcatalog, choose filters, and pin that selection. An artist page offers Pin beside the artist's name; the pin previews the artist's albums, or their tracks where they have none, and Compact counts the albums. Album and playlist pages do not offer pinning. In Customise Home, a neutral gear beside **MUSIC SOURCES** opens the same tab.

On an empty Home (no pins and no collections, a collections list still loading counting as none), the question, the search entry, its suggestions when there are any and the line of sources (shown then even where the left rail shows) sit centred in the pane, the crimson bloom centred behind the search with them, followed by a pin glyph, **Pin any catalogue or saved search to see it here.** in `textSecondary`, and a neutral **Customise Home** text button with the tune icon. Once the first content preview or collection arrives, the hint goes and the whole block, bloom included, glides to the top (450ms, ease in-out; at once under reduced motion) to make room for the sections. Centring leaves out the mini-player's slot while it slides away under the search, so its coming back moves nothing. Home doesn't promote collections for now: Your collections shows only once there is at least one (nothing while the list loads), with no invitation to make the first.

Pins are stored on this device, separately for each server identity (with an address fallback on older servers). Each pin retains its catalog metadata, filters, display labels, preview choice and position. The same catalog can be pinned with different filters. Disabling or temporarily losing a source does not delete its pins.

Adaptive previews use the existing `ShelfHeading`, source icons, typography and artwork resolver. The optional Home name replaces the heading, or labels the individual card in a grouped album-folder row; the destination and its title remain unchanged. The subtitle names the source, Folder or Artist where applicable, saved filters and the catalogue description. View All always opens the original saved destination and filters.

Pinning takes one tap and saves **Automatic**. Customise Home offers an optional **Home name**, **Automatic / Small preview / Large preview / Shortcut only**, drag reorder and confirmed unpin. Tap the name/pencil to edit it; clearing it restores the original title. The four illustrated preview choices save immediately in the existing anchored picker. The picker uses four columns when they fit, two on narrower panes, and one at large text sizes, and retains its outside-tap, Escape, Back and idle dismissal. Unpin and naming dialogs center in the whole window. Explicit compact preferences remain shortcuts.

Automatic uses the contents and the plugin's preview hint:

- A local album folder starts with one square cover, album title and artist at ordinary card size (up to 176dp). Both the cover and View All open the original folder. Recognition requires complete, unfiltered folder membership, one real library album ID, canonical album metadata and an exact match with the album's full track membership. Titles and shared covers are not identity evidence. Unknown totals, incomplete listings, missing metadata, duplicate tracks and the library's `unknown_album` bucket remain rows. Verification is bounded to 200 children and at most three additional pages per listing; nested/multi-disc folders remain folder rows. This uses today's folder IDs and APIs without direct album pinning or backend changes.
- Two or more consecutive verified album-folder pins with the same card size share a **PINNED FOLDERS** row instead of a separate full section per folder. Each card retains its album cover, title, artist and optional Home name, without a separate View All action beneath it. Tapping the card opens its original folder with its saved filters, including when two folders identify the same album. These remain folder pins; direct album pinning is not offered. Cards wrap on wide panes and swipe on phones; every pin remains accessible. Automatic and Small use ordinary cards; explicit Large uses cards capped at 320dp. Different card sizes, other preview types and explicit shortcuts break the run. Only immediate neighbours combine. Reordering and unpinning update the grouping without changing saved pin order or preferences.
- A loose-track folder shows three or four existing playable rows per column to match neighbouring content on wide Home panes (four when standalone), or three on narrow panes, in source order. Mixed children keep their order and existing track, album and folder row types and actions.
- An album catalogue with `card_size: large` gets a square lead cover beside two rows of smaller covers on a wide Home pane. The lead includes the intervening caption and frame height, so its artwork and caption bottom-align with the second row. The lead and small cards have touching highlight frames; their frame insets provide all the space between artworks. Small covers stay between 120dp and 200dp, with a two-by-two side grid preferred as soon as it fits; three available albums use one stacked side column. Extra width adds side columns and fetches more albums. The lead's cap follows two 200dp covers plus that caption/frame extent. A standard catalogue divides its width into equal covers capped at 176dp, keeping at least 120dp where multiple covers fit. Both layouts budget their frames and gaps. In Large mode, one or two available albums use equal large cards capped at 320dp, with a 240dp minimum where the wide pane can accommodate it. Beside a collage, these cards (including single-album folders) share its lead-cover size, bounded by their own column width. Cover sizing is independent of the original folder title or its Home name. Columns too narrow for a readable collage fall back to equal covers. No wide preview scrolls horizontally.
- A local artist previews albums supplied by My Library. Each opens its own album. When the artist has no album children, retain a playable local track list with the same neighbour-aware three/four-row limit on wide panes or three on narrow panes, in source order, including loose and compilation tracks. Nested album metadata on a track does not turn it into an album card.
- Album/playlist catalogues use the same artwork layouts, including My Library’s leading **Singles & loose tracks** playlist. Preserve item order and destinations; a playlist does not force the whole preview into rows. Adjacent Large previews are planned independently and can both use collages in one row.
- `preview.type: none` becomes a shortcut in Automatic. **Small preview** always shows content and explicitly chooses an equal-cover row for album catalogues, overriding a large-card hint. Tracks and mixed folders use short ordered lists, up to three rows per column. **Large preview** requests the lead-cover collage for album catalogues even when the plugin gives a small-card or no-preview hint; it uses the same width-based capacity and fetching as a source-requested collage. Track and mixed lists set to Large show up to six rows per column. Single-album folders explicitly set to Large use a large card too, including on phones. Adjacent folder cards group only with the same chosen size; changing the choice updates grouping and the background layout plan. Large folder cards swipe on phones with the next cover partly visible and wrap on wide panes. Automatic album folders start with ordinary covers and may grow into spare space beside a Large preview; track/mixed contents retain their playable rows. The choice persists per pin without changing source metadata. **Shortcut only** always suppresses the content preview.

Home list previews add columns as their allocated width grows: each column needs at least 480dp scaled for text, with 32dp between columns. Balance consecutive items down the left column, then down the next, retaining the same keyboard and accessibility order. A short list splits too (three items across two columns becomes two then one); a single item keeps one column’s width. Automatic lists choose three or four rows per column on wide panes, matching the estimated height of neighbouring content: ordinary album covers typically get three, taller collages four. Standalone lists keep four; narrow panes use three. A short neighbouring list can also set the height, while adjacent Automatic lists with enough items for either length keep four. Small preview means a short list of three rows per column; Large preview means a longer list of six rows per column, on phones as well as wide panes. Keep these same Small/Large labels for artwork and lists. The row planner uses the selected list length; fetch capacity reserves up to four rows for Automatic so fitting a neighbour reuses loaded items. Plugin artwork-size hints do not directly change list length. Legacy saved List preferences keep five rows per column; List remains absent from the current preview picker. Multi-column rows keep their metadata beneath titles, with normal actions and dividers. Row keys follow item identity (including separate occurrences of repeated items), so enqueue feedback cannot move to another item. Rebalancing columns clears keyboard focus and its history within that preview, preventing Enter from enqueueing a different track; width changes that keep the same slices retain focus. Standalone list placeholders use the same column geometry; Home uses the shared pin-area shimmer described below. Fetch capacity covers both possible artwork and list layouts within the existing 64-item bound.

Layout uses the available Home content width, with the wide arrangement starting at 800dp (scaled for text), independent of the outer window. A content-aware row planner compares full-width sections, equal or unequal columns, and short sections stacked beside a collage. It uses actual loaded item counts, folder wrapping, cover geometry and estimated section heights, including list dividers. Each candidate fits Automatic list lengths against columns with fixed content heights before scoring; stacked lists share that height budget. Ties retain more items. This stays in the geometry-only worker and adds at most four list-length comparisons per column, with no new network requests or widget measurements. A dynamic program chooses the lowest-cost sequence of contiguous row templates, balancing scroll height, empty area and additional readable catalogue covers. This is optimal within the bounded template/width choices, rather than an unrestricted rectangle-packing solution. At most six columns are considered; readable-cover minimums and text-scaled pane thresholds further constrain them.

After rows are chosen, a single pass checks independent Automatic artwork previews beside a Large preview. Promote to Large only when the result fits within the row’s existing estimated height, fills more of its area and keeps at least as many items visible. A single album or album-folder cover can match the neighboring collage’s lead cover. Explicit Small, grouped folder cards, tracks, shortcuts and narrow panes retain their chosen treatment. Promotion is local to that layout: it does not change saved preferences or fetch more catalog items. The result stays in the existing bounded layout cache.

For example, four pinned folders that would wrap beside Top Releases instead get a full-width row, followed by a full-width releases row with more covers. Shorter sections can still share space: the folder/Qobuz/artist example stacks the folder and artist on the left with the collage on the right. A left-hand collage can stack the following two ordinary sections on its right. All templates consume consecutive pins in reading order, and never cross shortcut or legacy-preview boundaries. Shortcuts form groups only with their immediate shortcut neighbours. Their cards share the available row width up to a 480dp scaled maximum, with top-aligned titles and bottom-aligned attribution. Each compact row takes the natural height of its tallest card, with 16dp padding and a 12dp title/footer gap; short rows do not inherit height from other rows. New or shorter metadata can grow or shrink the row. The plugin’s small source icon sits next to the source name, filters and item count; long text wraps and every card retains its full tap target. Narrow panes stack everything in pin order and use a swipeable album row with part of the next cover visible. Covers stay square and capped. Search and collections keep their existing positions. With no collections and up to four shortcuts only, those shortcuts sit beneath the centered search invitation.

Keep 32dp between major Home sections, 24dp between pinned previews, 12dp between headings and content, and 32dp bottom padding. Long headings wrap instead of crowding View All; the divider is omitted when it will not fit. Home holds the entire pinned area behind one standard two-shelf shimmer while saved pins, module capabilities, preview contents (including legacy previews and shortcut counts), folder verification and section geometry settle. Partial results never reveal individual previews or provisional arrangements. This placeholder is independent of the eventual layout. Failures count as settled: the final view retains the heading and destination with Retry, and unavailable sources do not block other pins. Pull-to-refresh, the existing hourly refresh and library revisions invalidate recognition with the normal preview cache and use the same loading gate. Missing artwork uses the existing fallback. Reduced-motion mode keeps placeholders static.

Section packing starts after the frame once all preview data has settled, using Flutter `compute` (a separate isolate on native desktop/mobile; the current event loop on web). Subsequent geometry changes are debounced by 40ms. Phone and single-section plans skip worker startup because they need no search. Only immutable dimensions, counts and section kinds enter the worker, with no library objects, artwork or render-object measurements. One job per Home section runs at a time; intervening resizes coalesce to the latest request and stale results cannot replace a newer layout. Until a plan matches the current width, text metrics, grouping and content counts exactly, the standard shimmer stays visible. Cached matching plans reveal immediately. Previously mounted previews stay hidden while replanning, preserving their last rendered scroll extent, row state and enqueue feedback. This prevents a temporary shimmer from clamping the scroll offset; a finished shorter layout releases the reserved space. A resize that keeps the same list slices also retains keyboard focus, but hidden controls cannot activate or receive traversal. Tab can leave the hidden pins for visible controls, and revealing the plan does not steal focus back. A worker failure reveals a usable stacked arrangement instead of leaving Home loading indefinitely.

Completed section plans and album geometry each have bounded 32-entry caches. Pane width, text metrics, preview shapes/preferences and loaded item counts determine their keys; playback, hover, image decoding and unrelated rebuilds do not rerun the optimiser. Font line heights and heading widths have separate bounded caches. Flutter still performs its normal widget layout and painting; section heights in the optimiser are estimates, not a promise of pixel-perfect packing for arbitrary long text.

Adaptive catalogue fetches use 8/16/32/64-item buckets, sized for a possible full-width preview. The planner and displayed preview share that one request; candidate arrangements cause no extra network calls. Counts come from loaded, displayable children rather than potentially misleading totals. Resizing within a bucket reuses its request. Artist previews retain the existing 100-item probe but phone album rails build only visible and nearby covers. Folder recognition is cached by unfiltered folder ID and revision, independently of display limits and filters, so grouping and resized or filtered pins share the verification. Presentation providers release their subscriptions when unused. Successful listings and recognition results share a cache capped at 32 inactive entries, evicting the least recently used entries without background timers; active previews remain available. Pull-to-refresh and the existing hourly refresh still invalidate source data and recognition. Regression tests check request reuse, cache eviction and lazy cover construction.

Pins use format version 3. Old noncompact layouts migrate to Automatic so existing folder pins benefit immediately. Explicit Compact layouts, saved destinations, filters, names and order survive. The old renderers remain compatible with version 3 records carrying those legacy enum names, but the editor offers only the four current choices.

The adaptive Home tests can optionally generate local screenshots by setting `KALINKA_REVIEW_DIR` to an output directory. Generated captures are not tracked; `docs/review/adaptive-home/` is ignored. The captures render real Flutter Home screens with representative API fixtures and bundled fonts; optional artwork comes from `KALINKA_REVIEW_ART`. `test/adaptive_home_test.dart` covers small/large single-album cards and folder grouping, the full-width four-folder/Top Releases example, the three-pin example, album and loose-track folders side by side, zero pins, shortcuts only, one catalogue, large text and a 1024×600 split-pane harness. The current main shell itself chooses a single pane at 1024×600; the additional harness constrains the real Home to 592dp beside the existing 432dp player to exercise the split-kiosk case without changing global shell breakpoints.

`test/home_section_planner_test.dart` exercises a real isolate, bounded caching, failure retry, resize coalescing, stale-result rejection and disposal during a calculation. Pure planner tests cover row choices, ordering and cover bounds.

To try this with a library, run the client normally, open a folder/catalogue/artist and tap its pin once. Return Home and use Customise Home to rename, change preview preference, reorder or unpin. Existing pins migrate when loaded. No demonstration data is added to the production client or the user's stored pins.

Catalog, album, artist, playlist and collection rows still open pages. Back restores the originating visit, filters and position as described in the [browsing design guide](browsing-design-guide.md).

## Backend capability and pagination contract

Plugin SDK 3.14 adds `ModuleCapability.CATALOGS = "catalogs"` to the existing capability enum. Input plugins declare it through `InputModule.capabilities()`, the same method used for `ai_search`. The default does not report `catalogs`, and implementing `browse` alone does not imply catalog availability.

The server includes declared capabilities in each `/server/modules` entry's `capabilities` string list, in enum order. Disabled plugins, builtins and receiver-only plugins expose no capabilities. My Library (`localfiles`) and Jamendo declare `catalogs`; the UPnP receiver does not. Out-of-tree plugins such as Qobuz, Tidal and Spotify must declare the capability in their own packages and require SDK >= 3.14 before their Home tiles appear. The app has no plugin-specific detection.

REST API 0.18 ships this contract. The app does not gate source tiles on the API version: missing `catalogs` means no source tile, including on older servers. There is deliberately no name-based allowlist or fallback probing of every plugin.

Example module metadata:

```json
{
  "name": "example_source",
  "title": "Example Music",
  "enabled": true,
  "state": "ready",
  "builtin": false,
  "capabilities": ["ai_search", "catalogs"]
}
```

The root `GET /browse` listing now honours `offset` and `limit` (default 10), with `total` counting all sources. Source tiles, Discover, catalog cards and collections share a helper that reads every root page until an empty page or `offset >= total`. Root IDs remain `kalinka:<source>:catalog:root`; the app uses each returned ID verbatim and never manufactures one. Each provider keeps its own filtering and ordering.

## Catalog metadata and filters

Existing BrowseItem metadata supplies everything else: a stable `kalinka:<source>:catalog:<id>` identity, `can_browse`, a catalog title, optional image/description, `filters`, and optional `sections`. A folder layout is still a catalog and can be pinned. A section's View all opens that section's own catalog page with the applicable parent filters.

Each plugin must expose its own subcatalog tree and filter declarations. For example, multiple release or editorial lists and their genre vocabularies belong in plugin responses; the app does not flatten or invent a provider-specific taxonomy. Genre choices use the existing `/browse/{catalog_id}/filter/{field}/values` API. Pins send only filters supported by their saved catalog schema. If a plugin removes a catalog or changes its schema, the preview reports a loading error and users can browse the updated source and replace the pin.

The backend test suite covers capability reporting and root pagination. Frontend coverage lives in `browse_root_test.dart`, `catalog_sources_test.dart`, `pinned_catalogs_test.dart`, and `catalog_home_ui_test.dart`.
